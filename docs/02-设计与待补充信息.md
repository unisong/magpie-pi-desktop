# 设计：Magpie ↔ Pi-Desktop

## 1. 结构

一个 Magpie 插件，加上一个由 Magpie 维护、Pi-Desktop 加载的插件文件夹（0.2.0 起）：

```
Magpie (127.0.0.1:3425)                          Pi-Desktop 0.22
┌──────────────────────────────────┐            ┌──────────────────────────────────────┐
│ agent 插件 pi-desktop-app（仅连接） │            │ 本地插件 local.magpie-gateway          │
│  检测 ~/.pi-desktop               │            │  就是左边写的那个文件夹，不复制          │
│  connect() 返回整份 manifest      │            │  每次启动重读，host-core 建 provider 行 │
└──────────────┬───────────────────┘            └───────────────▲──────────────────────┘
               │ 模型一变就重写                                  │ 加载本地插件（一次）
               └──► ~/.config/magpie-pi-desktop/plugin/manifest.json

        Magpie 网关 /v1/chat/completions  ◄──── Pi-Desktop 会话按所选模型请求，带密钥 magpie-pi-desktop-app
        （多供应商调度、分组、回退、用量统计都在这里）
```

- **Magpie 一侧**：`@magpie-community/agent-pi-desktop`，id `pi-desktop-app`，仅连接模式（模型在 Pi-Desktop 里逐会话选择，和 pig/Pi 一样）。`pi-desktop` 被 Magpie 自己的会话功能占用，插件不能用。
  - 有了它，Pi-Desktop 在 Agent 页有自己的一行。`magpie visible pi-desktop-app …` 能限定它看到哪些模型。用量和路由规则按密钥 `magpie-pi-desktop-app` 归属。
  - 它的 `config` 就是 `~/.config/magpie-pi-desktop/plugin/manifest.json`。`connect()` 返回 manifest 的每个顶层键，外加一个 `magpie` 键（网关地址和密钥名，给 Magpie 判断"已连接"和体检脚本用）。Magpie 的模型变化时会再调一次 `connect()`，文件随之更新。
- **Pi-Desktop 一侧**：用户用"加载本地插件"把这个文件夹加载一次。
  - manifest 声明 provider：`baseUrl` 指向 Magpie，`apiStyle: chat_completions`，`authKind: api_key`，模型带 `thinkingLevels` 和 `defaultThinkingLevel`。超过 64 个时分成 `magpie`、`magpie-2`…多个 provider。
  - `main` 指向 `manifest.json` 自己：Pi-Desktop 要求有入口文件，JSON 文件作为模块加载时没有任何钩子。所以文件夹里只有这一个文件，不含代码。
  - 用户在设置里给每个 provider 填一次密钥 `magpie-pi-desktop-app`。
  - 插件只有 `provider.register` 这一个权限，不跑代理扩展，不读写文件，也不联网。
- **Codex 流程**：本方案只新增一个代理 id 和一个 Magpie 自有文件，不碰 `~/.codex/config.toml`、`providers.json`、已有插件条目、路由分组。`verify/codex-invariants.mjs` 用前后快照检查这一点，覆盖 Codex 的 `config.toml` 和模型目录（`magpie-models.json`）、Magpie 的供应商和逐模型设置、Codex 的接入记录、网关探测和 `magpie codex` 输出。
  - 例外：Magpie 每次同步目录（包括加插件时）都会重写 Codex 的模型目录 `~/.codex/magpie-models.json`。内容由供应商和可见规则决定，加本插件不改变这些输入，脚本会列出目录里增减的模型。

## 2. 考虑过但没采用的方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 直接写 `pi.sqlite` | 否决 | host-core 独占、WAL 实时、schema 有版本；密钥要加密进 `secrets/` |
| Bun 宿主入口推送配置（kimi-desktop 模式） | 否决 | Kimi 有本地 API，Pi-Desktop 没有可供外部调用的写接口 |
| companion 读取桥接文件 | 否决 | `fs.read` 根只允许 workspace/userSelected；绕开权限用 Node fs 不合规 |
| agentExtensions 调 `extensions.model.configure` 改会话模型 | 否决 | 需要高风险 `agent.extension`，还会覆盖用户在对话里的选择 |
| 把模型清单打进 `.piplug`（0.1.2） | 被 0.2.0 取代 | 清单固定，Magpie 一变就要重新打包、重装 |
| Magpie 直接维护本地（开发）插件的 manifest | **0.2.0 采用** | host-core 每次启动重读，密钥保留，64 上限靠分卡片解决；都在沙箱里验证过 |
| 插件代码在 Pi-Desktop 里即时更新 provider | 否决 | 插件 API 没有增改 provider 的调用；`desktop.*` 需要高权限 `desktop.control` |
| 写 `~/.pi/agent/models.json` 让 Pi-Desktop 一键导入 | 不作为主路径 | 这个文件归官方 Pi 和 Magpie 内置 Pi 行管理；导入只是一次性复制，用量也会记到 Pi 头上。文档里作为"零代码备选"说明 |

## 3. 已知限制
- 不是即时的。Pi-Desktop 0.22.0 只在启动、启用插件、加载本地插件时读 manifest 里的 provider 和模型。Magpie 改了模型后，Pi-Desktop 要重启，或把 Magpie Gateway 禁用再启用，才跟上。端口变化也一样，密钥不用重填。
- Pi-Desktop 0.22.0 只对 manifest 里声明的模型带推理等级；它自己发现的模型一律默认 off。所以模型和推理等级都写在 manifest 里。
- Pi-Desktop 开着时会发现文件变了，重载插件并提示 `Reloaded Magpie Gateway`；这不更新 provider 行。
- Pi-Desktop 限制每个插件 provider 最多 64 个模型。超过时会出现多张卡片（Magpie、Magpie 2…），每张各填一次密钥；以后新出现的卡片到时再填。模型可能在卡片之间挪动。
- Magpie 没给推理等级的模型保持 Pi-Desktop 的通用设置：七个档位都能选，默认 off。Magpie 的 `ultra` 档在 Pi-Desktop 里没有对应档位，不带过去。
- 在 Magpie 关掉 Pi-Desktop 这一行会清空 manifest。Pi-Desktop 保留最后读到的 provider，要在扩展页卸载 Magpie Gateway 才会消失。
- 本地插件在 Pi-Desktop 里算开发插件：行上带"本地"标记，没有自动更新。

## 4. 需要你补充的信息（已按默认值继续）

| 问题 | 默认值 | 何时需要改 |
|---|---|---|
| Magpie 网关端口 | `3425`（来自 `~/.codex/config.toml` 的 base_url） | 改过 Settings › 端口或用了 `MAGPIE_ADDR` |
| Pi-Desktop 数据目录 | `~/.pi-desktop` | 设置过 `PI_DESKTOP_DATA_DIR` 或迁移过存储位置 |
| Pi-Desktop 插件 id | `local.magpie-gateway`（沿用你的 `local.` 前缀习惯） | 想用别的名字。安装后再改会生成新 provider，需要重填密钥 |
| 接口格式 | `chat_completions`（与 Magpie 内置 Pi 适配一致） | 想改用 `responses` |
| 是否发布到社区市场 | 只准备好 registry 条目和 README，不提交 PR | 你确认后再发 |
| 在真实环境安装 | 等你确认 | 会改 Magpie `plugins.json`（新增一条），并在 Pi-Desktop 新增一个 provider |
